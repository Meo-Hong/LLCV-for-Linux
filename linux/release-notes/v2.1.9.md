## 한국어

Windows LLCV 2.1.8~2.1.9 업데이트를 리눅스판에 반영했습니다. 리눅스판 2.1.8은 따로 배포하지 않았고, 그 내용도 여기에 들어 있습니다.

### RGB 입력

- **BGR24, BGR32(32비트 RGB), RGB24**를 재생, 스크린샷, 녹화에 지원합니다. UVC 장치가 RGB32로 내보내는 영상은 리눅스에서 BGR32(커널에 따라 `XR24` 또는 `BGR4`)로 보입니다.
- RGB는 **픽셀 형식**에서 직접 고릅니다. 자동 선택은 Windows판처럼 NV12, YUY2, UYVY만 고릅니다. 이전 버전은 자동에서도 BGR24를 고를 수 있었습니다.
- **SDR 색 범위** 설정과 드라이버가 알려 준 범위가 이제 RGB에도 적용됩니다. 알려 준 범위가 없으면 Full입니다.
- 녹화는 RGB를 **BT.709 Limited 4:2:0**으로 변환합니다(무손실 RGB 아님). 파일을 만들기 전에 녹화 스레드가 변환 시간을 잽니다. 평균이 프레임 시간의 75 %를 넘거나 한 번이라도 한 프레임 시간을 넘으면, 녹화를 시작하지 않고 녹화 해상도나 프레임 상한을 낮추라고 안내합니다. 고른 FPS를 알아서 낮추지는 않습니다.
- RGB 입력에는 장치 내부 HDR→SDR 톤매핑 요청을 보내지 않습니다(Windows 2.1.9와 같음).
- RGB는 YUV보다 대역폭이 커서 USB 3.0에서는 1080p30 이하가 현실적입니다. 장치가 목록에 올린 형식 코드를 그대로 요청하므로, 같은 배치를 다른 이름으로 보고하는 장치도 열립니다.

### UYVY 입력

- **UYVY(8비트 4:2:2)**를 재생, 스크린샷, 녹화에 지원합니다. 셰이더가 바이트 순서를 바로 읽어서 CPU 변환이나 복사가 늘지 않습니다.

### 업스케일링·진단

- **CMAA2 → NIS 업스케일링 안정성**: 아주 조밀한 프레임이 CMAA2 작업 버퍼(후보·혼합 항목·위치 목록)를 넘치면, 일부만 안티에일리어싱한 화면을 보여 주지 않고 그 프레임만 CMAA2를 건너뜁니다. NIS 확대는 계속하고, 다음 정상 프레임부터 CMAA2가 다시 적용됩니다.
- **지원하지 않는 픽셀 형식 안내**: LLCV가 쓸 수 없는 형식만 제공하는 장치도 목록에 나타나고, 설정 화면이 그 형식 이름(최대 3개)을 알려 줍니다. 건너뛴 형식과 프레임 크기는 모두 로그에 남습니다.
- 장치가 알려 준 한 줄 크기(bytes per row)가 형식에 비해 작으면 그 모드로 시작하지 않고 이유를 알려 줍니다. 스트림마다 처음 버린 프레임의 크기를 로그에 남깁니다.

Windows판과 다른 점:

- Windows판은 BGR24에 해당하는 RGB24와 XRGB(RGB32)만 지원합니다. 리눅스판은 바이트 순서가 반대인 RGB24도 받습니다.
- 리눅스판은 UYVY도 녹화합니다. HDYC는 V4L2에 별도 형식이 없어서 장치가 UYVY로 보고합니다.
- NVIDIA VSR은 리눅스에 없습니다. V4L2 영상은 항상 위에서 아래 순서라서 상하 반전 처리도 필요 없습니다.

기존 설치 경로, 설정, 사용자 지정 단축키는 그대로 유지합니다. 픽셀 형식을 직접 BGR24로 골라 두었다면 그대로 BGR24를 씁니다.

## English

This release brings the Windows LLCV 2.1.8 and 2.1.9 updates to Linux. Linux 2.1.8 was not released separately; its changes are included here.

### RGB input

- **BGR24, BGR32 (32-bit RGB) and RGB24** work for playback, screenshots and recording. Video that a UVC device sends as RGB32 appears on Linux as BGR32 (`XR24` or `BGR4`, depending on the kernel).
- Select RGB under **Pixel format**. Like the Windows build, Auto now picks only NV12, YUY2 or UYVY; earlier versions could pick BGR24 automatically.
- The **SDR color range** setting and the range the driver reports now apply to RGB. Without a reported range, RGB is Full.
- Recording converts RGB to **BT.709 Limited 4:2:0** (not lossless RGB). Before the file is created, the recording thread times the conversion. If the mean exceeds 75 % of the frame time, or any sample exceeds one frame time, recording does not start and asks for a lower recording resolution or frame limit. The selected frame rate is never lowered on its own.
- RGB input sends no vendor HDR-to-SDR tone-mapping request, as in Windows 2.1.9.
- RGB needs more bandwidth than YUV, so on USB 3.0 expect 1080p30 or lower. Capture requests the exact format code the device listed, so devices that report the same layout under another name also open.

### UYVY input

- **UYVY (8-bit 4:2:2)** works for playback, screenshots and recording. The shader reads the byte order directly, so there is no extra CPU conversion or copy.

### Upscaling and diagnostics

- **Safer CMAA2 → NIS upscaling**: if a very dense frame overflows the CMAA2 work buffers (candidate, blend-item or location list), that frame skips CMAA2 instead of showing partial anti-aliasing. NIS keeps scaling, and CMAA2 returns on the next normal frame.
- **Unsupported pixel format notice**: devices that offer only formats LLCV cannot use appear in the list, and settings name those formats (up to three). Every skipped format is logged with its frame sizes.
- A mode whose reported bytes per row are too small for its format no longer starts, and the reason is shown. The first rejected frame of each stream is logged with its size.

Differences from the Windows build:

- Windows supports RGB24 (the Linux BGR24 layout) and XRGB (RGB32). Linux also accepts RGB24 with the opposite byte order.
- Linux also records UYVY. HDYC has no separate V4L2 format, so devices report it as UYVY.
- NVIDIA VSR is not available on Linux. V4L2 video is always top-down, so no orientation handling is needed.

Installation paths, settings and custom shortcuts are kept. A pixel format explicitly set to BGR24 stays BGR24.
